# 澄 · 前端与动效重构（设计系统 2.0）

分支：`claude/frontend-animation-redesign-2e4f23`。基线为主目录 0.6.0 之后尚未提交的工作（动效、伪息屏、听歌喜好、曲库跳转），原样快照为本分支第一个提交，再在其上重构。

## 设计原则

1. **贴合主题**：保留并强化两套既有视觉语言，不另起炉灶。
   - **澄 · 经典**：暖纸色底、墨色文字、陶土色强调（深色为夜墨 + 琥珀）。圆角、柔和阴影、悬浮式迷你播放器、封面柔光背景——像光透过清水，呼应“澄”。
   - **终末地 · 工业**：纸白 / 枪灰、信号黄、直角模块、粗细分割线、切角按钮；动效更短、更“机械”，页头黄色定位条在进页时像信号一样延伸。
2. **动效只走合成线程**：全部转场都是 `transform` / `opacity` 的 Web Animations 或 CSS transition，主线程在渲染列表、轮询播放状态时不会卡住已经开始的动画。不永久提升图层、不做循环动画、不做全屏模糊。
3. **每个操作都有过渡，且可被打断**：新的状态总会取消它所取代的旧动画；快速连点以最后一次为准。
4. **颜色过渡自然**：颜色令牌注册为 `@property <color>`，主题、封面取色变化时整套配色在 520ms 内平滑过渡；系统状态栏 / 导航栏用同一时长和曲线在原生侧插值。
5. **减少动态效果**：系统设置或应用内开关打开时，所有移动和颜色渐变直接落到终态。

## 性能手段

- **页面不再 `display:none`**：隐藏页改用 `content-visibility: hidden`，保留布局与滚动位置，切页时不必整页重新排版。`[hidden]` 属性语义不变，现有脚本和测试照常判断。
- **暖页**：`content-visibility` 会丢掉隐藏页的 GPU 纹理，而 WebView 的光栅和绘制串行，光栅会卡住正在运行的动画。曲库、播放、我的三个顶级页隐藏时改为 `opacity: 0` 并保留纹理，切页只做合成。启动 1.2 秒后才开始保留，每次只恢复一页，避免长时间占住主线程。颜色渐变和模态抽屉期间退回冷页，否则隐藏页要跟着逐帧重绘或重算 inert 样式。
- **页面几何固定**：迷你播放器不再占据文档流，页面高度不随它变化，切页时没有重新布局。它隐藏时保留盒子但不绘制，切歌不会重绘它。
- **隐藏时不更新进度**：隐藏页的滑块和时间文字不随 `timeupdate` 改写，重新显示时直接落到当前进度。
- **曲库选择结果缓存**：4,000+ 首歌曲的筛选、排序与喜好排除按条件记忆，导航与普通重绘不再重复过滤、排序和序列化。
- 列表入场最多编排前 14 项；封面柔光用 40×40 画布预先模糊后放大，静态合成，不做实时滤镜。

- **两帧交接**：切到冷页（子页面，或暖页尚未就绪时）时，第一帧只提交旧页面的离场动画，下一帧再解锁新页面。切到暖页时两者同帧开始。
- **切歌少阻塞**：隐式存盘（播放/暂停/进度/导航）在队列未变时合并，转场结束后空闲执行；切歌后回读 4,000+ 首队列推迟 650ms；原生侧进度与历史两次 70KB 设置读写合并为一次并推迟 700ms。队列变化和需要报错的保存仍同步执行。
- **系统栏同步渐变**：`appearance-bars` 携带时长，原生用 `ArgbEvaluator` 插值状态栏 / 导航栏颜色。
- 终末地与经典的底色沿用 0.6.0 真机审阅过的色值。

### 切歌时的原生卡顿

`UiTrackChangeProbeTest` 记录每次切歌期间 Android UI 线程上超过 30ms 的 Looper 分发，并从另一线程采样调用栈。

| 指标（4,161 首，每轮 10 次切歌） | 修复前 | 修复后（3 轮） |
| --- | --- | --- |
| 播放中：单次最长分发 | 246–289ms | 30–69ms |
| 播放中：每次切歌阻塞合计 | 556–716ms | 30–180ms |
| 暂停中：单次最长分发 | 265–284ms | 35–51ms |
| 暂停中：每次切歌阻塞合计 | 679–812ms | 69–116ms |

上表在屏幕锁定、WebView 不出帧时测得，只用于前后对比。解锁亮屏复测（2 轮，每轮 6 次播放中 + 4 次暂停切歌）：播放中单次最长 32–92ms、合计 62–162ms；暂停中单次最长 31–42ms、合计 35–133ms。

找到并修复的三个阻塞点：

1. **整个队列经 Binder 发给系统**（约 250ms，每次切歌两次）。Media3 每次 timeline 更新都调用 `MediaSession.setQueue`，序列化 4,161 个条目。会话播放器现在不提供 `COMMAND_GET_TIMELINE`。
2. **音频端口缓存重读**（100–210ms）。Android 7 上只要有 `AudioDeviceCallback`，每次输出变化都会在 UI 线程调用 `AudioSystem.listAudioPorts`，并等待 audioserver 重开输出。现在不再注册回调：音频接收器在 Android 8 以下不再持有 context；输出路由文字改为跟随 UI 轮询，在后台线程刷新（2 秒一次，输出变化后 2 秒内不读）。
3. **封面在 UI 线程缩放**（偶发 185–811ms）。`MediaSession.setMetadata` 会缩放超限的封面。会话封面现在解码时就限制在 320px 以内。

取舍：外部控制器（如蓝牙设备的“正在播放列表”）看不到完整队列；当前歌曲、元数据、上一首 / 下一首不受影响。路由文字最多延迟约 2 秒更新。

已在真机验证：媒体键上一首 / 下一首可切歌；`MediaController` 能读到当前歌曲并切下一首；通知栏有上一首 / 暂停 / 下一首和封面（208–233px）；输出 96kHz、float、libflac；探测到的音频能力与接收器默认值一致；路由文字可通过轮询恢复。

### 解锁亮屏帧率（无障碍关闭）

`UiFrameProbeTest` 用进程内 `FrameMetrics` 统计渲染帧（`>34ms` 指该帧从 vsync 到完成的总耗时，含流水线延迟，不等于掉帧），rAF 反映主线程。两种主题合计 38 个样本，“改前”为切歌修复后、暖页之前，“改后”为两轮结果：

| 场景 | 首帧 改前 → 改后 | rAF 最长间隔 改前 → 改后 | 超过 34ms 的帧 改前 → 改后 |
| --- | --- | --- | --- |
| 底部导航切页 | 77–98 → 74–137ms | 43–106 → 29–53ms | 20% → 3.4–3.7% |
| 抽屉开 / 关 | 59–113 → 61–130ms | 18–104 → 18–131ms | 6.5% → 4–5% |
| 进入 / 离开歌词 | 59–77 → 69–104ms | 33–100 → 39–109ms | 21% → 14–21% |
| 切歌 | 171–198 → 175–262ms | 51–108 → 57–136ms | 27% → 36–38% |
| 列表滚动 | 16–17 → 4–18ms | 36–46 → 49–162ms | 1.5% → 0–6% |
| 明暗切换 | 291–334 → 292–322ms | 139–151 → 140–165ms | 31% → 32% |

**切页慢帧的成因**（DevTools trace）：转场开头约 17 个 tile 的 GPU 光栅（`DoEndRasterCHROMIUM`，76–127ms，含 trace 开销）卡住了正在运行的离场动画；进出播放页时迷你播放器改变内容区高度，引发约 500 个对象重新布局并重新光栅，离场结束时还会再跳一次。动画中段本来就稳定在 15–18ms。

**暖页的代价**：
- 静音播放时进程 CPU（单核占比）冷页 46–47%、暖页 47–50%，帧率相同。每轮第一次测量都偏高（约 57–71%），与冷暖顺序无关，属于启动效应，已排除。
- 恢复暖页时主线程有一次约 100–160ms 的停顿（上表列表滚动的 rAF 最长间隔）。它发生在封面变色约 1.5 秒后或抽屉关闭约 0.8 秒后，且避开转场和切歌；此时点击的响应会稍慢。合成帧不受影响。
- 进入歌词页首帧约多 10–30ms，但转场中的慢帧不变或减少。

切歌修复前后的同条件对比（两次都开着无障碍，绝对值偏大）：同步处理 548–748ms → 111–189ms，首帧 825–1014ms → 369–459ms，窗口内渲染帧数 15–26 → 33–43。

**测试陷阱：不要在计时前调用 `getUiAutomation()`。** 首次调用会连接无障碍客户端，`AccessibilityManager.isEnabled()` 变为 true，WebView 开始维护无障碍树，直到进程结束。实测抽屉首帧约 99ms → 约 395ms，切页约 100ms → 约 300ms。截图和 `dumpsys` 都会触发。普通用户不受影响，开启屏幕阅读器的用户会受影响。旧版探针走 `dumpsys`，首帧普遍约 350ms，就是这个原因。现在 `UiFrameProbeTest` 不再使用 `UiAutomation`，`UiMotionDeviceTest` 把截图移到所有计时之后，两者都断言无障碍处于关闭状态。

**尚未达到的部分（如实记录）**

- 切歌还不够顺：经典主题在封面取色渐变期间，一半以上的帧超过 34ms（每轮 18–22 帧 / 29–39 帧），终末地只有 3–7 帧。暖页之前已有同样的表现（同场景 6/35 和 23/36），但当时两轮差异很大，所以无法断定这次是否变差。主要嫌疑是颜色令牌逐帧重绘整页，尚未处理。
- 明暗切换约 32% 的帧超过 34ms，首帧约 300ms。
- 切到冷页（设置、统计、歌词等子页面）的第一帧仍有约 60–100ms 停顿，主要是 Adreno 505 为新页面执行 GPU 光栅（文字字形占约一半）。切到暖页时点击到首帧约 100ms，主要是 `render()` 约 40ms 和样式、绘制、提交。
- 真实插拔耳机 / 蓝牙时的路由更新未验证（路由恢复只做过轮询模拟）；修复后的实际听音未验证（测试全程静音）。
